# AutoHistory

Telegram-бот — цифровая сервисная книжка автомобиля. Реализован по `AutoHistory_Архитектура_и_ТЗ.pdf` (версия 1.0, 21.09.2026) и `AutoHistory_бизнес_гипотеза.pdf`. При расхождениях применяется ТЗ: бесплатный пилот, cron, ручной пробег, без веб-приложения и платежей.

## Возможности

- Регистрация с выбором и подтверждением IANA-пояса; до 50 владельцев и 3 автомобилей на владельца.
- До 500 записей ТО на автомобиль: дата, пробег, вид работ, необязательные стоимость, СТО, примечание и одно JPEG/PNG до 5 МиБ. Сумма хранится как Decimal; пропуск отличается от нуля.
- Пошаговый ввод, проверка каждого поля, «Назад», «Пропустить», «Отмена», сводка и подтверждение. Черновики живут 30 минут; перезапуск сбрасывает только незавершённый ввод.
- История владельца с подробностями, открытием фото и подтверждённым удалением. История для СТО — последние 2 календарных года или всё время, по 5 записей.
- Один план на стандартный вид работ; интервалы 100–100 000 км и/или 1–60 календарных месяцев. Исходная точка подтверждается явно; можно взять последнее соответствующее ТО. Для «Другое» план не создаётся.
- Напоминания за 500 км / 7 дней и при наступлении срока по любому порогу; запрос нового пробега раз в 30 дней без обновления. Окно 09:00–20:00 в поясе владельца.
- PDF всей истории с кириллицей, переносами, повторяемой шапкой таблицы, известными расходами и числом записей без суммы. Фото и Telegram ID не включаются. Одна генерация одновременно в рабочем потоке, временный файл удаляется после отправки/ошибки.
- Исправление пробега через подтверждение, удаление записи, автомобиля и аккаунта, каскады и пересчёт планов.

## Устройство

Python 3.13, aiogram 3, PostgreSQL, asyncpg, ReportLab. Две точки входа используют один сервисный слой:

```text
Telegram → app.bot → app.service → PostgreSQL
                         ↓
                    app.reports → PDF → Telegram
cron → app.jobs.tick → app.service → notification_outbox → Telegram
```

`app/domain.py` содержит чистые правила и валидацию; `app/service.py` — владельческий доступ и транзакции; `app/db.py` применяет нумерованные SQL-миграции с контрольными суммами. `app/bot.py` реализует личные диалоги и короткие непрозрачные callback. `ops/` содержит инструкции для эксплуатации. Redis, HTTP API и APScheduler не нужны.

Проверка владельца выполняется через связанный с доверенным `from.id` AuthContext. Пять обработчиков и пул из пяти соединений; события одного пользователя обрабатываются последовательно. Создание ТО и авто защищено `creation_key` и сравнением тела запроса. Изменения автомобиля блокируют его строку; запись, пересчёт и outbox фиксируются одной транзакцией. Сообщение об успехе отправляется после COMMIT.

## Быстрый локальный запуск

Для уже подготовленного Windows-компьютера доступны **«Запустить бота.cmd»** и **«Остановить бота.cmd»**. Этот режим сам запускает отдельную локальную PostgreSQL-базу и ежеминутную проверку напоминаний. Подробности: [запуск на Windows](docs/local-windows.md). Следующие команды описывают ручной запуск с самостоятельно подготовленной БД.

Нужны Python 3.13 и PostgreSQL 17 или 18. Создайте **отдельную** БД `autohistory` и пользователя с паролем. Создайте бота через BotFather. Не вставляйте токен в код и не используйте рабочую БД для тестов.

```powershell
python -m venv .venv
.venv\Scripts\python -m pip install -r requirements.lock
Copy-Item .env.example .env
```

На Linux команды аналогичны: `python3 -m venv .venv`, `.venv/bin/python -m pip install -r requirements.lock`, `cp .env.example .env`.

Заполните `BOT_TOKEN` и `DATABASE_URL` в `.env`. Пример формата подключения: `postgresql://autohistory:password@127.0.0.1:5432/autohistory`. Для специальных символов в пароле используйте URL-кодирование. Затем:

```powershell
.venv\Scripts\python -m app.db
.venv\Scripts\python -m app.bot
```

В личном чате нажмите `/start`. Команды: `/help`, `/cancel`, `/delete_me`. У одного токена должен работать только один polling-процесс. Входящий HTTP-порт не нужен.

Проверка напоминаний выполняется **отдельно**:

```powershell
.venv\Scripts\python -m app.jobs.tick
```

Для постоянной работы установите ежеминутный запуск этой команды в планировщике; целевой вариант ТЗ — Linux cron ниже. Сам бот не запускает второй планировщик.

## Docker Compose на VPS

1. Скопируйте `.env.example` в `.env`, заполните токен и `POSTGRES_PASSWORD`. Для Compose удобно использовать случайный hex-пароль не короче 32 символов. БД доступна только во внутренней сети Compose, без публикации порта.
2. Подключите отдельное надёжное хранилище журнала удалений. Укажите абсолютный путь в `.env`: `DELETION_JOURNAL_HOST_DIR=/mnt/independent-storage/autohistory-deletions`. Каталог должен существовать и быть доступен UID 10001. Локальный путь `./backups/deletions` предназначен только для разработки. Перед пилотом с реальными данными независимое хранилище обязательно по ТЗ.
3. Выполните:

```bash
docker compose build
docker compose up -d postgres
docker compose run --rm bot python -m app.db
docker compose up -d bot
docker compose logs --tail=50 bot
docker compose exec -T bot python -m app.jobs.tick
```

`compose.yaml` использует `autohistory:1.0.0`, `postgres:17.9-bookworm`; Dockerfile — `python:3.13.12-slim-bookworm`. Все Python-зависимости закреплены в `requirements.lock`. После сборки используйте тот же образ для бота и cron. Перед обновлением версии сохраните дамп и предыдущий образ; изменения уже применённых SQL-файлов запрещены, добавляйте новую миграцию.

## Cron, контроль и логи

Установите `ops/autohistory.cron` в crontab пользователя, имеющего доступ к Docker, заменив `/opt/autohistory` на путь проекта. Создайте `/var/log/autohistory` с правами для этого пользователя. Установите `ops/logrotate.conf` для хранения файлов cron 14 дней. Контейнерные логи ограничены ротацией по объёму, а не точным возрастом; для строгого срока 14 дней настройте удаление в журнале Docker/системном сборщике.

`tick` получает session advisory lock на отдельном соединении. Параллельный проход сразу завершается. Перед каждой отправкой повторно проверяются владелец, цикл, стадия и окно. В сетевом вызове транзакция БД не удерживается. Проход рассылки ограничен по времени, остаток очереди обрабатывается следующим cron. Ограничения очереди: до 10 отправок/сек суммарно и до одной/сек в чат.

- 429 сохраняет `retry_after` в БД и останавливает отправки до этого срока, в том числе после перезапуска.
- Сеть/5xx: 1, 5, 15, 60, 180 минут, затем `failed`.
- 403 отключает доставку и отменяет pending пользователя; `/start` восстанавливает только актуальные события, не затрагивая sent.
- Уже отправленное уведомление текущего цикла повторно не открывается. Устаревшие циклы хранятся 90 дней после завершения; ключи текущего цикла не удаляются.

`python -m app.jobs.health` проверяет возраст tick (до 5 минут), failed и свободное место (не менее 20%), возвращает ненулевой код при проблеме. Проверьте `backups/last-success` и журнал backup отдельно: они находятся на хосте. Ответственный за пилот ежедневно проверяет эти показатели и ошибки копирования. Токены, SQL-параметры и содержимое сообщений не пишутся в прикладной журнал ошибок; пользователю выдаётся безопасный текст с request_id.

## Резервное копирование и восстановление

На VPS нужны `age`, `rsync`, GNU tar и доступ по SSH к **независимому** носителю. Создайте пару age-ключей; закрытый ключ храните вне VPS. Скопируйте `ops/backup.env.example` в `ops/backup.env`, заполните публичный ключ, адрес хранения и путь журнала, установите права `600`.

`bash ops/backup.sh` потоково шифрует `pg_dump -Fc`, копирует шифротекст и архив журнала на независимый носитель. Отметка успеха создаётся только после обеих копий. Локальные шифротексты удаляются через 7 дней; **такой же срок нужно настроить на удалённой стороне**. Ежедневная копия журнала не заменяет его независимое постоянное хранение: удаления после последнего дампа должны пережить потерю VPS. Если журнал недоступен, удаление не подтверждается.

Удаления записываются с fsync до удаления в БД. Если последующий COMMIT не удался, журнал всё равно сохраняет намерение удаления: при восстановлении приватность имеет приоритет. Журнал содержит только UUID объекта, тип и время, без текста ТО. После успешного копирования запускается очистка устаревших временных PDF и журнала старше семи дней.

Восстановление выполняется в **новую** БД, а не поверх рабочей:

```bash
bash ops/restore.sh /secure/AutoHistory_20260924T021500Z.dump.age /secure/age-private-key autohistory_restore_20260924
```

Далее, до запуска polling и cron:

1. Подключите актуальный независимый журнал удалений.
2. Установите `DATABASE_URL`, указывающий на новую БД. При работе через Compose передайте его явно через `docker compose run --rm -e DATABASE_URL=... bot ...`, поскольку в Compose рабочий URL задаётся отдельно.
3. Выполните `python -m app.db` и `python -m app.jobs.replay_deletions` с этим подключением.
4. Проверьте машины и историю контрольного владельца, отсутствие удалённых объектов; выполните tick и health тестовым ботом.
5. Только после проверки переключите рабочий контейнер на восстановленную БД. Сохраните измеренное время восстановления.

Цели из ТЗ: потеря данных не более 24 часов, восстановление до 4 часов. Локальный тест дампа не доказывает эти цели на VPS; до приглашения пользователей обязательна репетиция с удалённой зашифрованной копией. Дамп хранит Telegram file_id, **не оригиналы фотографий**. Пересланные PDF и уже доставленные сообщения удалением аккаунта не отзываются.

## Тесты

```powershell
.venv\Scripts\python -m pip install -r requirements-dev.txt
$env:TEST_DATABASE_URL='postgresql://test_user:password@127.0.0.1:5432/autohistory_test'
$env:TEST_PG_BIN='C:\Program Files\PostgreSQL\18\bin'
.venv\Scripts\python -m pytest -q
```

На Linux используйте `export TEST_DATABASE_URL=...`, `export TEST_PG_BIN=/usr/lib/postgresql/17/bin` и `.venv/bin/python -m pytest -q`. Пользователю тестовой БД нужны права CREATE SCHEMA; для теста восстановления — также CREATE DATABASE. Тесты создают схемы с уникальными именами и отдельную БД восстановления, затем удаляют **только их**. Никогда не задавайте рабочий URL. Без `TEST_DATABASE_URL` интеграционные тесты явно пропускаются; без `TEST_PG_BIN` пропускается только реальный pg_dump/pg_restore.

Проверяются F1–F7: реальный PostgreSQL, миграции, владение, повторные и параллельные сохранения, ограничения, календарь, корректировки, удаление базового ТО, outbox, 429/403/таймауты, приватность PDF, длинные поля, 500 записей, восстановление дампа и журнал удалений. Telegram-диалоги исполняются через aiogram Dispatcher с имитацией API: тесты не отправляют сообщения реальным людям. Тестовые данные находятся в `tests/conftest.py`, `tests/test_reports.py` и фабриках `tests/test_service.py`.

`tests/test_capacity.py` печатает локальные метрики PDF и 100 сервисных операций с конкурентностью 5. Это не замер p95 от Telegram Update до API на целевом VPS. Сценарии ручной приёмки и фактический протокол — `docs/acceptance.md`.

## Существенные ограничения

Пробег не считывается из автомобиля и не прогнозируется. Если Telegram доставил уведомление, но ответ потерялся или процесс упал до записи sent, повторная попытка может дать дубль: это доставка «хотя бы один раз». В узком промежутке между последней проверкой состояния и сетевой отправкой изменение плана или удаление аккаунта не может отозвать уже начатый запрос Telegram. Код и тесты не заменяют проверку токена, доступа к VPS, независимого хранилища и реальной доставки.

Официальные технические источники: [aiogram polling](https://docs.aiogram.dev/en/latest/dispatcher/long_polling.html), [Telegram Bot API](https://core.telegram.org/bots/api), [Telegram FAQ](https://core.telegram.org/bots/faq), [блокировки PostgreSQL](https://www.postgresql.org/docs/17/explicit-locking.html). Шрифты Ubuntu поставляются в `assets/fonts` вместе с `UFL.txt`; [лицензия Ubuntu Font](https://canonical.com/legal/font-licence).
